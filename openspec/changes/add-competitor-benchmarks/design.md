## Context

No benchmark code exists. The product forbids shelling out to `git`, but that rule covers the run-staged binary only — the bench harness is dev tooling and may use the git CLI freely to build fixtures. Competitors span five runtimes (Node, Go, Python, Ruby, Rust), so the harness must stay runtime-neutral. See proposal.md for motivation and specs/benchmarks/spec.md for the required behavior.

## Goals / Non-Goals

**Goals:**
- One script, few files, readable in a single sitting.
- Measure the tool, not npm/npx/pip resolution or `git commit` itself.
- Equivalent configs across tools so numbers are comparable.

**Non-Goals:**
- CI integration or regression gating (noisy shared runners; add later if wanted).
- Benchmarking real linters (eslint/prettier) — their cost would swamp tool overhead.
- Memory/RSS measurement (hyperfine doesn't do it; add `/usr/bin/time -l` later if needed).
- Windows support for the harness (bash; macOS + Linux only).

## Decisions

**D1. Bash + hyperfine, no custom harness.** `bench/run.sh` drives `hyperfine`, which already gives warmup, repeated runs, stats, JSON/markdown export, `--reference` baseline, `--prepare` (untimed per-iteration reset). Alternatives: a Rust `criterion` bench (can't time external processes well, adds deps), a Node/Python harness (adds a runtime the comparison is supposed to be neutral to). Rejected.

**D2. Layout.**
```
bench/
  run.sh            # entry point: prereq checks, fixture build, tool loop, --verify
  report.sh         # renders results/ as markdown (re-runnable without re-benchmarking)
  .npmrc            # ignore-scripts: lefthook's postinstall would write lefthook.yml into the repo
  package.json      # pins lint-staged, nano-staged, lefthook (npm dist) for local node_modules/.bin
  README.md         # how to install competitors, how to run
  results/          # hyperfine JSON (gitignored)
  RESULTS.md        # generated, committed when publishing numbers
```
Per-tool configs are generated by `run.sh` (one `write_config_<tool> <scenario>` function per tool, heredocs) rather than stored as ~36 template files — scenarios differ only in globs and command, so generation is shorter than templates.

**D3. Fixtures.** For each (scenario, file count) build a pristine repo once in `$TMPDIR/run-staged-bench/<scenario>-<n>/pristine`: init, commit base files, modify + `git add` the staged set (and for partial-staging, add further unstaged edits). All tool configs are written into the base commit (pre-commit refuses uncommitted configs). Each hyperfine iteration's `--prepare` runs `rsync -a --delete pristine/ work/`; rsync rather than `rm -rf && cp -R` because hyperfine's cwd is `work`, which must keep existing. Copying is untimed. Files are tiny generated `.js`/`.ts`/`.css`/`.md` text so every tool's default type detection is happy; concurrency scenario splits them into 4 disjoint extensions, one per task.

**D4. How each tool is invoked** (direct runner call, never `git commit`, hyperfine `-N` so no shell wrapper is timed):

| Tool | Install | Invocation | Parallel config |
|---|---|---|---|
| run-staged | `cargo build --release` | `target/release/run-staged --quiet` | groups parallel (default) |
| lint-staged | bench/node_modules | `node_modules/.bin/lint-staged` | default (globs concurrent) |
| nano-staged | bench/node_modules | `node_modules/.bin/nano-staged` | whatever its default is |
| lefthook | bench/node_modules or brew | `lefthook run pre-commit` | `parallel: true` |
| pre-commit | `uvx`/`pipx` | `pre-commit run` | none (sequential) |
| prek | brew/cargo | `prek run` | same priority → parallel |
| hk | brew/cargo | `hk run pre-commit` | default |
| stagelint | cargo | its run command | default |
| overcommit | `gem install` | `.git/hooks/pre-commit` (installed by `overcommit --install`) | `parallelize` default |

pre-commit / prek use `repo: local`, `language: system` hooks so no environment install happens in the timed path; warmup runs absorb any first-run cache creation. Exact flags for hk, stagelint and overcommit are verified during implementation against each tool's `--help`; `--quiet`-equivalent flags are used where available so terminal rendering is not measured.

**D5. Commands.** overhead/scaling: `true`. concurrency: `sleep 0.5` (POSIX `sleep` accepts fractions on macOS and GNU). Batch mode (all files in one invocation) everywhere, since that's every tool's default and keeps 10 000 files to one spawn per task. Per-file mode is not compared — not all tools have it.

**D6. Reporting.** hyperfine `--export-json results/<scenario>[-n].json --export-markdown` with `--reference` set to run-staged gives mean ± σ, min/max and relative columns for free; `--sort mean-time` orders fastest first. `run.sh` concatenates the markdown tables under a header with date, `uname -a`, CPU model/cores (`sysctl`/`lscpu`) and a tool-version list. The concurrency parallelism factor (2.0 / mean) and sequential marker are added with one `jq` pass over the JSON. `jq` and `rsync` become prerequisites.

**D7. Partial-staging check.** Timing and correctness are separate. The timed run uses a no-op command. After it, each tool runs once, untimed, on a `partial-probe` fixture whose command is `sh probe.sh`: the probe records that it ran and lists any argument file still containing `UNSTAGED_MARKER`. From that, `results/unstaged.tsv` records per tool whether it hides unstaged edits and whether they survived. Every tool is timed, including ones that don't hide (run-staged itself protects partially staged files by never re-staging them, so an "n/a" rule would drop the baseline). Replaces the `--conclude` idea: a shared conclude hook can't tell which tool it follows. `sh` wrapper because nano-staged can't exec an absolute path.

**D8. Defaults.** `--warmup 3 --runs 10`; file counts `10,100,1000,10000`; overridable via `run.sh --runs N --files 10,100 --tools a,b --scenarios x,y`. `RUN_STAGED_BIN` points at a prebuilt binary instead of building the workspace.

## Risks / Trade-offs

- [Tool flag/config drift across versions] → versions recorded in RESULTS.md; config functions are small and one per tool.
- [Thermal/background noise on laptops] → warmup + 10 runs, σ shown; README advises closing heavy apps and plugging in power.
- [Unequal defaults make comparisons unfair] (e.g. one tool stashes in "overhead", another doesn't) → each tool runs in its default safety mode in every scenario and the table notes which tools stash; partial-staging isolates that cost explicitly.
- [10 000-file fixtures are slow to copy in `--prepare`] → untimed; only total wall-clock of the bench run suffers. Lower `--files` for quick runs.
- [overcommit invoked via hook script adds a shell] → noted in the table footnote; it's how overcommit is run in practice.
