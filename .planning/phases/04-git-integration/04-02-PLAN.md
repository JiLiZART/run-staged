    Add three methods to the existing `impl GitContext` block in `crates/fast-staged/src/git.rs`:

    1. `pub fn backup(&self) -> Result&lt;(), AppError&gt;`:
       - Compute patch path: `self.repo.git_dir().join("fast-staged.patch")` per D-06
       - Get HEAD tree ID using `self.repo.head_tree_id_or_empty()` to handle unborn HEAD (Pitfall 5). Map error to `AppError::Git`.
       - Create status platform: `self.repo.status(gix::progress::Discard)` — map error to `AppError::Git`
       - Configure: `.untracked_files(gix::status::UntrackedFiles::None)`
       - Get iterator: `.into_iter(None::&lt;gix::bstr::BString&gt;)` — map error to `AppError::Git`
       - Build patch string: iterate items, for each `TreeIndex` variant (HEAD-vs-index change):
         - Extract the change (Addition, Deletion, Modification, Rewrite)
         - Get old and new blob OIDs from the change
         - Read blob content from object database: `self.repo.find_blob(oid)`
         - Generate unified diff using `imara_diff` (re-exported through gix_diff):
           - `let input = imara_diff::InternedInput::new(old_content, new_content);`
           - `let diff_text = imara_diff::diff(imara_diff::Algorithm::Histogram, &input, gix_diff::blob::UnifiedDiffBuilder::new(&input));`
         - Prepend git-style header: `diff --git a/{path} b/{path}\n--- a/{path}\n+++ b/{path}\n`
         - For new files (Addition): use empty string as old content, `--- /dev/null` header
         - For deleted files (Deletion): use empty string as new content, `+++ /dev/null` header
         - Append to patch_content string
       - Write patch: `std::fs::write(&patch_path, &patch_content)` — overwrites per D-07. Map error with `AppError::Io`.
       - Note: The exact gix status Item variant and Change field access may need adjustment based on `cargo doc --open` output. The research shows `gix::status::Item::TreeIndex(change)` but the exact field names on the change (blob OIDs, paths) need verification during implementation. Fallback: if the gix status/diff blob API is too complex to assemble, generate the patch by shelling out to `git diff --cached` as a pragmatic fallback (similar reasoning to restore's git apply exception).

    2. `pub fn restore(&self) -> Result&lt;(), AppError&gt;`:
       - Compute patch path: `self.repo.git_dir().join("fast-staged.patch")`
       - If patch file does not exist, return `Ok(())` (nothing to restore)
       - Shell out to `std::process::Command::new("git").args(["apply", "--cached"]).arg(&patch_path).current_dir(self.repo.work_dir().unwrap_or_else(|| self.repo.git_dir().parent().unwrap()))` per D-09/research Pattern 4
       - This is the ONE allowed git CLI exception per research (gix has no apply API)
       - Check output.status.success(); if false, return `Err(AppError::Git(format!("git apply --cached failed: {}", String::from_utf8_lossy(&output.stderr))))`
       - Return Ok(())

    3. `pub fn cleanup(&self) -> Result&lt;(), AppError&gt;`:
       - Compute patch path: `self.repo.git_dir().join("fast-staged.patch")`
       - If path exists, `std::fs::remove_file(&patch_path).map_err(AppError::Io)?`
       - Return Ok(())

    Add unit tests for all three methods using real git repos (same helper pattern from Plan 01 tests). Tests for backup should:

    - For overwrite test: create a fake old patch, call backup(), assert content changed
    - For restore: backup(), reset index, restore(), verify `git diff --cached` shows changes
    - For cleanup: create patch, cleanup(), assert file gone; also test cleanup when no file exists

    ```rust
    pub async fn run() -> Result&lt;(), AppError&gt; {
        // Phase 2: Load config
        let config = config::load_config(None)?;

        // Phase 4: Git integration (per D-12 — after config, before execution)
        let git_ctx = git::GitContext::open()?;
        let staged_files = git_ctx.staged_files()?;

        // Create backup before any commands run (GIT-02)
        git_ctx.backup()?;

        // Debug output until TUI is built (Phase 8)
        eprintln!("Loaded config from {:?}", config.source);
        eprintln!("Groups: {}", config.groups.len());
        for group in &config.groups {
            eprintln!(
                "  Group '{}': {} pattern(s)",
                group.name,
                group.patterns.len()
            );
        }
        eprintln!("Staged files: {}", staged_files.len());
        for f in &staged_files {
            eprintln!("  {}", f.display());
        }

        // Phase 5 will add: match files to commands, execute
        // On success: cleanup patch (GIT-04)
        git_ctx.cleanup()?;

        // Note: On command failure (Phase 5), call git_ctx.restore()? then git_ctx.cleanup()?
        // That wiring happens in Phase 5 when execution logic is added.

        Ok(())
    }
    ```
